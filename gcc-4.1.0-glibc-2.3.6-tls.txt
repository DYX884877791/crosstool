📜 证据一：glibc 官方 Bugzilla 的明确记录
glibc 官方的 Bugzilla 中存在一个专门的条目，标题直接点明了问题。

Bug 编号：build/13810

标题：install_root broken for install-headers

关键内容：报告和讨论中明确指出，make install-headers 过程会因 install_root 失效而出现问题。例如，在交叉编译时（cross-compiling=yes），显式传递 install_root=/var/tmp 可以工作，但这恰恰反证了在不显式传递或变量丢失时，默认行为会失败。

这个官方 Bug 的存在，是“已知缺陷”最权威的定义性证据。

📋 证据二：Buildroot 开发者对问题现象的精确描述
Buildroot 作为一个成熟的嵌入式构建系统，在其邮件列表和代码提交中，直接描述了与你遇到的完全一致的现象：install_root 在子 make 中变为空值。

提交信息：在 Buildroot 的一个 git 提交（package/glibc: use DESTDIR instead of install_root to fix build issue）中，开发者 Thomas Perale 写道：

“The problem being that the install_root variable is for some reason lost along the way. We definitely pass it during the staging installation step, but then glibc calls a sub-make and in that submake, install_root is empty.”

这精确地复现了你观察到的现象：安装步骤中 install_root 丢失，导致子 make 试图将文件安装到文件系统根目录（/usr/include/...），从而因权限不足而失败。

🔧 证据三：crosstool-ng 社区的同类问题报告
crosstool-ng 是专门用于构建交叉编译工具链的工具，其邮件列表中记录了与你的构建环境高度相似的问题。

报告内容：一位开发者在构建 glibc 2.8 时遇到了完全相同的 /usr/include/limits.h 权限拒绝错误，并分析道：

“Seems like 'install_root' parameter isn't passed to the sub-make process and that's why install procedure tries to perform action from FS root.”

这证明该问题并非孤立，而是在 crosstool 类构建流程中长期存在的一个已知障碍。

⚙️ 证据四：问题根源的延伸——make 版本兼容性
进一步的调查揭示，该缺陷在某些情况下与 GNU make 的版本有关，这解释了为什么它是一个“已知”但可能时隐时现的缺陷。

Gentoo Bug 331975：该报告明确指出，make-3.82 版本会“loses that install_root setting”，导致 glibc 尝试安装到 / 目录。

Buildroot 邮件列表：同样提到，问题在使用 make 4.4.1 时出现，而 install_root 在 make 4.2.1 中则不会丢失。

这表明，缺陷的触发与构建环境中 make 工具对命令行变量（MAKEFLAGS）的处理方式变化有关，是一个涉及多组件交互的已知兼容性问题。

这个 buffer overflow detected 错误和之前的 install_root、open 问题属于同一类：旧版工具（这次是 binutils 的 ar）的潜在缺陷，被现代系统的安全机制（glibc 的 FORTIFY_SOURCE）捕获并主动终止了。

🎯 根本原因：ar 命令的已知缺陷被暴露
你正在使用的 x86_64-unknown-linux-gnu-ar 来自一个较旧的 binutils 版本（很可能是 2.16.x 系列）。这个版本的 ar 在构建静态库时，代码中存在一个缓冲区溢出缺陷。

具体来说，在 binutils 的源码文件 bfd/archive.c 中，第 2071 行附近使用了 sprintf 来格式化归档文件的头部信息，而没有检查目标缓冲区的大小：

c
sprintf (hdr.ar_size, "%-10d", (int) mapsize);
当 mapsize（即 libgcc.a 的大小）的数值较大时，格式化后的字符串长度就可能超过 hdr.ar_size 字段的固定容量，从而造成溢出。

在旧环境下，这个溢出可能不会被发现，或者只是悄悄覆盖了相邻数据。但现代 glibc 启用的 FORTIFY_SOURCE 安全机制，会将在编译时已知固定大小的缓冲区操作替换为带安全检查的版本（如 __sprintf_chk）。一旦检测到实际写入长度可能超出，就会直接调用 __fortify_fail，打印 *** buffer overflow detected *** 并终止程序。

这一现象在历史上已有明确记录：2005年就有开发者在 Fedora Core 4 上使用 binutils-2.16 的交叉 ar 时遇到了完全相同的错误，并最终定位到 bfd/archive.c 中的 sprintf 调用；当时的一个变通方法就是禁用 FORTIFY，禁用后 ar 便不再报错。

🛠️ 解决方案
方案一：禁用 FORTIFY_SOURCE（推荐优先尝试）
这是最直接的绕过方式。你需要在构建 binutils 本身的时候，确保编译器没有定义 _FORTIFY_SOURCE 宏。

如果你的 binutils 已经编译好了，就需要重新编译它。在配置或编译 binutils 时，通过 CFLAGS 显式地取消该宏的定义：

bash
CFLAGS="-U_FORTIFY_SOURCE" ./configure ...
# 或者，如果已有 CFLAGS，可以追加：
CFLAGS="$CFLAGS -U_FORTIFY_SOURCE" make
-U_FORTIFY_SOURCE 会取消任何已定义的 _FORTIFY_SOURCE 宏，从而关闭这些编译时的缓冲区溢出检查。历史记录表明，这个方法是有效的。

方案二：手动修补 binutils 源码
如果希望从根本上修复问题，而不是关闭安全检查，可以应用针对该缺陷的补丁。

OpenEmbedded 项目曾为 binutils-2.16.1 提供了一个专门的补丁 binutils-2.16-ar-overflow.patch，用于修复 ar 的缓冲区溢出问题。你可以为你的 binutils 源码应用类似的补丁。

其核心思路是将不安全的 sprintf 替换为能够限制写入长度的 snprintf，或确保目标缓冲区足够大。例如，修改后的代码可能类似于：

c
snprintf (hdr.ar_size, sizeof(hdr.ar_size), "%-10d", (int) mapsize);
应用补丁后，重新编译并安装 binutils 即可。

🎯 根本原因：echo 命令的兼容性问题
glibc 2.3.6 的 csu/Makefile 在生成 version-info.h 时，使用 echo 命令来输出包含转义字符的字符串。然而，部分 /bin/sh 实现（例如在某些系统上作为 /bin/sh 的 dash）对 echo 命令的解析行为与 GNU bash 不同，无法正确理解这些转义序列，最终导致生成的文件中字符串的终止引号丢失，从而引发编译错误。

这个问题是 glibc 2.3.6 的已知缺陷，在 crosstool 和 crosstool-ng 社区早有记录，并有标准补丁。

🛠️ 解决方案
你有两种主要方式来解决这个问题，首选是应用官方补丁，这能从根本上修复问题。

方案一：应用 crosstool 官方补丁（推荐）
crosstool 社区为 glibc 2.3.6 提供了专门的补丁，其核心是将 csu/Makefile 中不稳定的 echo 命令替换为行为一致的 printf。

操作步骤如下：

下载补丁文件：获取 glibc-2.3.6-csu-Makefile.patch。这个补丁在 crosstool 的源码仓库中可以找到，其地址为：
http://crosstool.googlecode.com/svn/trunk/src/patches/glibc-2.3.6/glibc-2.3.6-csu-Makefile.patch

放置补丁：将下载的补丁文件放入你 crosstool-0.43 安装目录下的 patches/glibc-2.3.6/ 文件夹中。crosstool 在构建 glibc 时会自动应用该目录下的补丁。

重新构建：补丁就位后，重新运行你的构建流程。crosstool 会在解压 glibc 源码后自动打上此补丁，从而正确生成 version-info.h。
